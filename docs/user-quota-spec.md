# User Quota Specification

일일 한도의 집계 축을 **영상 단위에서 이용자 단위로** 옮긴다. 크롬 확장은 수정하지 않는다.

- 결정: 2026-08-10 (운영자)

**이 문서의 범위**: 이 서버가 **무엇을 받아 어떻게 집행하는가**만 다룬다. 앞단이 이용자를
어떻게 식별하고 누구에게 얼마를 주는지는 앞단의 정책이며 여기 적지 않는다 — 그 층은 별도
저장소에서 관리한다. 그래서 이 문서에는 구체적인 티어 이름도 상한 숫자도 나오지 않는다.
여기 있는 숫자는 **앞단이 아무 말도 하지 않았을 때 내려앉을 이 서버의 기본값**뿐이다.

---

## Overview

1. **집계 축 전환** — `action_logs`가 이용자를 기록하고, 모든 한도 검사와 `GET /api/limits`가 이용자 기준으로 답한다
2. **파괴적 행위 합산** — 초기화와 강제 재생성을 하나의 예산(4회/24h)으로 합친다
3. **업그레이드 재분류** — 확장의 깊이 올리기가 파괴적 예산을 먹지 않게 한다
4. **초기화 멱등성** — 지운 게 없으면 예산을 소비하지 않는다
5. **어드민 관측** — 면제는 유지하되 사용량은 기록하고 화면에 보인다
6. **한도값은 앞단이 알려준다** — 티어별 차등을 살리기 위해 상한을 헤더로 받는다
7. **잇기 표시 교체** — 배경 탐색 대신 사람이 실제로 한 수동 잇기를 센다
8. **운영 작업 식별자** — 앞단을 우회하는 스크립트는 전용 actor를 쓴다

---

## 1. 집계 축 전환

### 문제

`action_logs`에 이용자를 식별하는 열이 없다. `count_recent(action, video_id)`는 그 영상에 대한 **모든 사람의** 사용을 합산한다.

```
[지금]
이용자 A가 영상 X에 20번 생성  →  action_logs 20행 (누가 했는지 없음)
이용자 B가 영상 X를 처음 열면  →  남은 횟수 0 / 20   ← B는 손댄 적이 없다
```

한 사람의 사용이 다른 사람을 정지시키는 구조는 공개 서비스에서 성립하지 않는다.

### 요구사항

- 한도 검사·기록·조회가 **모두 같은 이용자 축**을 쓴다. 소비 경로는 생성·잇기 후보·업그레이드·초기화·강제 재생성 전부다.
- 이용자 식별자는 **앞단이 요청 헤더로 넘긴다.** 이 서버는 그 값을 **불투명한 문자열**로만 다룬다 — 무엇으로 만들어졌는지 해석하지 않고, 같은 값이면 같은 사람이라는 것만 쓴다. 식별자를 어떻게 만드는지는 앞단의 책임이므로 이 서버의 정확도는 그 층의 강도를 넘어설 수 없다.
- **식별자가 없거나 신뢰할 수 없으면 거절한다(fail-closed).** 영상 단위로 폴백하면 지금 문제로 되돌아간다.
- 이 헤더는 앞단이 붙인 것만 신뢰할 수 있다. 따라서 **이 서버는 앞단을 거치지 않는 경로로 도달 가능해서는 안 된다.** 그 보장은 배포 환경의 책임이고 이 서버는 검증하지 않는다 — 검증할 수단이 없기 때문이다(헤더는 누구나 붙일 수 있다).
- 기존 기록은 이용자를 사후 복원할 근거가 없다. **비운 채로 남기고 이용자별 집계에서 제외한다.** 공용 이용자로 채워 넣으면 지금 문제를 재현한다.

### 개인정보 원칙과의 관계

헌법 II(Privacy as Default)의 "사용자 식별 정보: 수집 안 함"과 닿는 지점이다. 공개된 개인정보 안내는 이미 다음을 명시하고 있으며, 이 변경은 그 범위를 넘지 않는다.

- 접속 IP 원문은 저장하지 않는다 — 이 서버에 도달하는 것은 앞단이 만든 **되돌릴 수 없는 식별자**뿐이다
- 그 값은 **사용량 제한에만** 쓰이며 이용자를 식별하거나 이용 내역을 프로필로 모으는 데 쓰지 않는다
- 확장이 설치 ID·기기 지문 같은 식별자를 만들어 심지 않는다

요구사항: 이용자 축 기록은 **한도 집행에 필요한 최소 범위**를 넘지 않는다. 한도 창(24시간)을 넘어선 이력은 집행에 쓰이지 않으므로 보존 목적이 없다. 안내 문구가 실제와 어긋나면 문구를 고친다 — 실제를 문구에 맞춰 숨기지 않는다.

## 2. 파괴적 행위 합산

### 문제

초기화와 강제 재생성이 **각각 독립 상한**을 갖는다. 표시는 둘 중 큰 값 하나만 보여준다.

```
[지금]  초기화 2회 + 강제재생성 2회 = 실제로는 4회까지 가능
        화면에는 max(2, 2) = 2 하나만 표시
```

한 예산처럼 보이는데 두 예산이다.

### 요구사항

- 두 행위를 **하나의 합산 예산**으로 집행한다. 상한은 **4회/24시간**(운영자 결정 2026-08-10 — 종전 실질 총량을 유지한다).
- 다음 회복 시각은 **가장 이른 기록이 창을 벗어나는 시점**이다. 합산에서는 어느 한 건만 빠져도 값이 줄기 때문이다.
- 링크 해제는 **이 예산에 넣지 않는다.** 아래 별도 항목 참조.

### 링크 해제를 제한하지 않는 이유

링크 해제는 잘못 연결된 링크를 **되돌리는 복구 행위**다. 한도는 비용과 가용성을 지키는 수단이지 정확성을 지키는 수단이 아니며, 틀린 링크는 한도로 막을 수 없다(횟수를 줄여도 틀린 링크는 그대로 남는다). 정확성은 검증 표시(`verified`)와 권한 요구가 담당한다. 복구 경로를 막으면 잘못된 상태가 고쳐지지 않은 채 남는다.

**알려진 표시 불일치**: 확장 배지 문구가 "초기화 · 해제"인데 실제 집계는 초기화 + 강제 재생성이다. 확장 무수정 원칙에 따라 지금은 문구를 고치지 않는다. 다음 확장 업데이트에서 정리한다.

## 3. 업그레이드 재분류

### 문제

확장의 API 래퍼가 재생성 요청에 `force`를 **무조건** 붙인다. 서버는 `force`를 보고 파괴적 행위로 판정한다. 그런데 확장에서 그 경로를 부르는 것은 **정렬 깊이 올리기 버튼**뿐이다.

결과: 업그레이드 전용 카운터가 도입 이후 **한 번도 기록되지 않았다**(실측 2026-08-10 — 전 기간 0건). 대신 업그레이드가 파괴적 예산을 소비한다. 확장은 "정렬 업그레이드 10 / 10"을 계속 만땅으로 보여준다.

### 요구사항

요청을 다음 세 갈래로 판정한다.

| 요청 형태 | 판정 |
|---|---|
| `force` + 깊이 지정 있음 | 업그레이드 |
| `force` + 깊이 지정 없음 + 그 영상의 최신 싱크가 **스탬프 이전 세대** | 업그레이드 |
| 그 외 `force` | 파괴적 재생성 |

- 두 번째 갈래는 구세대 싱크용 업그레이드 버튼을 구제하기 위한 것이다. 그 버튼은 깊이 인자 없이 호출하므로 첫 번째 조건에 걸리지 않는다.
- **판정 범위가 그 버튼보다 넓다는 것을 인정한다**(운영자 결정 2026-08-10). 같은 형태의 직접 API 호출도 업그레이드로 분류된다. 확장에는 강제 재생성 UI가 없어 일반 이용자는 그 경로를 탈 수 없고, 오분류가 나도 요청은 시킨 대로 수행되며 달라지는 것은 어느 예산이 줄어드는가뿐이다. 또한 구세대 싱크는 한 번 업그레이드되면 스탬프가 찍혀 조건에서 빠지므로 이 느슨함은 시간이 지나면 사라진다.
- 🔴 **한도 검사 위치를 진행 중인 잡에 합류하는 판정 뒤로 옮긴다.** 지금은 그 앞이라, 이미 도는 잡에 합류하는 재시도(연타)도 예산을 소비한다.
- 🔴 **재생성 직전의 기존 번역 보존 처리 순서를 바꾸지 않는다.** 분기를 옮기면서 그 단계를 건너뛰면 사람이 남긴 번역이 유실된다.

## 4. 초기화 멱등성

### 문제

응답이 유실되어 클라이언트가 재시도하면 서버는 그것을 새 초기화로 본다. 지울 것은 이미 없어 **아무 일도 일어나지 않는데 예산만 줄어든다.**

### 요구사항

- **실제로 지운 것이 있을 때만** 예산을 소비하고 기록한다. 삭제 결과 수량이 이미 응답에 포함되어 있다.
- 지울 것이 없는 요청은 성공으로 답하되 예산을 건드리지 않는다. GPU도 쓰지 않으므로 반복해도 해가 없다.

## 5. 어드민 관측

### 요구사항

- 어드민은 **거절만 면제받고 사용량은 기록된다.** 지금은 검사 자체를 건너뛰어 기록도 남지 않아, 화면이 소유자에게 항상 만땅으로 보인다(실측 2026-08-10 — 당일 5건·7일 63건을 쓴 상태에서 20/20 표시).
- 🔴 **면제 이용자의 응답은 "강제 아님 + 사용량 N"으로 답한다.** 한도를 강제하는 형태로 소진값을 보내면 확장이 차단 상태로 그린다. 확장 무수정 조건에서 표시와 실제를 일치시키는 유일한 방법이다.

---

## 6. 한도값은 앞단이 알려준다

### 문제

앞단은 이용자마다 **서로 다른 한도**를 줄 수 있다. 그런데 이 서버는 평평한 상수 하나로 집행한다. 두 값 중 **작은 쪽이 항상 먼저 걸리므로**, 앞단이 그보다 큰 값을 준 이용자는 그 차액에 영원히 도달할 수 없다.

```
앞단   이용자마다 다른 상한 (넉넉히 받은 이용자 · 적게 받은 이용자 · 면제)
여기   전원 같은 상수 하나              ← 넉넉히 받은 값은 이 상수로 잘린다
```

집행을 이 서버 한 곳으로 모으기로 한 이상(§1), 상한도 여기서 알아야 한다.

### 요구사항

- 앞단이 이용자 식별자와 함께 **그 이용자에게 허용된 한도값**을 전달한다. 이 서버는 그 값으로 집행하고 `/api/limits`에도 그 값을 담는다.
- **값을 못 받으면 자기 기본값으로 내려앉는다.** 요청을 거절하지 않는다 — 배포 순서(앞단 먼저 / 여기 나중)를 유연하게 두기 위해서다.
- 🔴 다만 그 상태는 **티어 무력화와 같다.** 기본값으로 내려앉았다는 사실이 로그에 남아야 한다. 조용히 넘어가면 "티어를 줬는데 왜 안 먹지"를 아무도 못 찾는다.
- 무제한을 뜻하는 값을 응답의 `limit`에 그대로 싣지 않는다 — 응답 계약의 `limit=0` 항목 참조.

## 7. 잇기 표시 교체

### 문제

확장 배지 "커버 잇기"가 세던 것은 **자동 후보 탐색**이었다. 사용자가 싱크 없는 영상을 열면 배경으로 나가는 요청이고, 사용자는 그것을 요청한 적도 없고 실패해도 볼 수 없다(확장이 설계상 조용히 삼킨다).

정작 사용자가 "커버 잇기"라고 생각하는 행위 — 검색 시트에서 원곡 주소를 넣어 직접 연결하는 것 — 은 이 서버에서 **아무 데도 세지 않는다**.

### 요구사항

- 자동 후보 탐색의 횟수 상한을 **없앤다.** 비용 상한은 이미 구조가 담당한다 — 양쪽 영상이 미디어 캐시에 있을 때만 검증 잡을 제출하고, 미스면 포기한다. 실측(2026-08-10): 유튜브 접촉 0회, 검증 잡 전체 하루 2~3건.
  - 🔴 **그 구조적 게이트를 끄는 것은 비용 상한을 없애는 결정과 같다.** 끄려면 그때 상한을 다시 논해야 한다.
- 그 자리에 **수동 잇기**를 이용자 단위로 세어 표시한다. 라벨과 내용이 처음으로 일치한다.
- 수동 잇기의 상한은 앞단이 알려주는 값을 따른다(§6).

## 8. 운영 작업 식별자

앞단을 우회해 이 서버를 직접 부르는 운영 스크립트(대량 인제스트·재생성 검증·벤치)는 이용자 식별자가 없어 §1의 fail-closed에 걸린다.

- 스크립트마다 **고유한 운영 식별자**를 쓴다(사람과 구분되는 이름). 사람의 예산에 섞이면 통계가 오염된다.
- 🔴 **"어드민 키면 식별자 없이 통과"로 풀지 않는다.** 그것은 §5가 고치는 "면제라서 기록이 없다"를 운영 작업에 대해 되살리는 것이다. 면제하더라도 기록은 남는다.
- 운영 식별자의 상한은 작업 성격에 맞게 넉넉히 두거나 면제한다 — 대량 인제스트는 원래 그런 작업이다.

## 응답 계약 (확장 무수정의 전제)

확장은 서버가 준 숫자를 그대로 그린다. 따라서 다음이 계약이며 깨면 화면이 깨진다.

- 필수 항목(강제 여부·생성·파괴적 행위·창 길이)은 **항상** 포함한다. 누락 시 확장에 방어 코드가 없다.
- 잔량은 **음수가 되지 않는다.** 사용량이 상한을 넘어도 0으로 자른다. 음수를 보내면 화면에 그대로 표시되고 소진 표시도 붙지 않는다.
- **상한 0을 "무제한"의 뜻으로 쓰지 않는다.** 확장은 그것을 `0 / 0` 소진으로 그린다. 무제한은 "강제 아님"으로 표현한다.
- 선택 항목(잇기·업그레이드)을 빼면 그 줄만 사라진다 — 의도적으로 숨길 때만 뺀다.
- 회복 시각이 없으면 안내 줄만 생략된다.

## 검증

- 이용자 A/B가 같은 영상에서 각자 상한까지 독립적으로 통과한다
- A가 다른 영상으로 옮겨도 같은 개인 예산을 이어 쓴다
- 식별자 부재·위조 요청은 거절되고 기록도 남지 않는다
- 합산 4회 경계: 초기화 2 + 강제 재생성 2 이후 다섯 번째가 거절된다
- 진행 중인 잡에 합류하는 요청은 어느 예산도 소비하지 않는다
- 지울 것이 없는 초기화는 예산을 소비하지 않는다
- 어드민은 상한을 넘겨도 통과하되 사용량과 기록이 증가한다
- 기존 이력(이용자 없음)은 어떤 이용자의 사용량으로도 세지 않는다

목 데이터로 대체하지 않는다. 라이브 검증은 전용 테스트 이용자와 전용 테스트 영상에서 수행해 운영 데이터와 섞지 않는다.
