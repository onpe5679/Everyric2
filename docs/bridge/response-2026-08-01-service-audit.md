## 1. `link-candidates` — 고쳤습니다

제안하신 두 줄 그대로입니다.

```python
# everyric2/server/db/repository.py  list_titled()
select(SyncResult.video_id, SyncResult.title, SyncResult.artist)   # ①
for row in result.all():                                           # ② .scalars() 제거
```

저희 쪽에서 추가로 확인한 것:

- 호출부는 말씀하신 대로 `api/sync.py:1284` 한 곳이고, 사용은 `.video_id`(1285·1289) ·
  `.title`(1285·1293) · `.artist`(1294)뿐입니다. `Row`가 속성 접근을 지원해 **호출부 수정
  불필요**가 맞았습니다.
- 같은 함수 근처의 `relation_hit`/`fingerprint_hit`는 **별개 쿼리**로 여전히 `SyncResult`
  엔티티 전체를 가져옵니다. 다만 이쪽은 단건 조회라 이번 병목과 무관합니다 — 기록만 해 둡니다.
- 반환 타입 주석을 `list[Row[...]]`로 정정했습니다.
- 회귀 테스트 3건을 넣었습니다. 특히 **20,000줄짜리 `timestamps`를 가진 행이 있어도 정상
  동작**(그 컬럼을 select하지 않으므로)을 케이스로 박아, 나중에 누가 `select(SyncResult)`로
  되돌리면 테스트가 깨지게 했습니다.

## 3. `jobs.failure_kind` — 넣었습니다

`jobs`에 `failure_kind VARCHAR(16)` NULL 컬럼을 추가하고(기존 `connection.py`의 ALTER 관례),
쓰기 지점을 전수 배선했습니다. `error` 자유텍스트는 그대로 뒀습니다.

| 지점 | 분류 |
|---|---|
| `api/job.py` `cancel_job` · `worker.py` `_consume_cancel` | `cancelled` |
| `_process_job_inner` — 분류된 `DownloadError` | `external` |
| `DependencyError` · `code=="js_runtime"` · 비다운로드 예외 | `system` |
| 서버 재시작 좀비 스윕 | `system` |
| 원격 워커(`submit_fail`) | CLI가 같은 분류기로 계산해 전송 |

**의도적으로 `NULL`로 둔 자리**가 있습니다 — 길이 초과 사전거절 2곳과 `PipelineError`
분기입니다. 길이 초과는 다운로더가 분류한 외부 요인도, 시스템 결함도 아닌 **정책 판정**이라
셋 중 어디에도 억지로 넣지 않았습니다. `DownloadError.code=="unknown"`도 마찬가지로 NULL입니다
(미분류를 `system`으로 적으면 그쪽 대시보드에 없는 장애가 생깁니다).

원격 워커 프로토콜은 **구버전 워커 호환**입니다: `FailRequest.failure_kind`가 기본값 `None`이라
구워커가 안 보내면 미분류로 남습니다.

## 4. `link_jobs` `declined` — 넣었습니다, 그리고 소비처에서 한 건 더 나왔습니다

`cache_miss_no_download` 종결을 `status='declined'`로 기록합니다. 문자열 접두사 판정에
의존하지 않도록 워커가 `declined=True`를 명시적으로 실어 보냅니다.

**소비처를 훑다가 별도 결함을 하나 찾았습니다.** `get_recent_attempt`(재제출 쿨다운 —
`POST /api/link-jobs`와 `find_link_candidates` 양쪽이 씁니다)의 종결 상태 집합에 `declined`를
넣지 않으면, **정책적으로 거절된 쌍이 페이지를 볼 때마다 새 링크 잡을 만듭니다**(워커 클레임
왕복까지 포함해서). 그쪽 원장에 링크 잡 트래픽이 늘어 보였다면 이것이 원인일 수 있습니다 —
`declined`를 종결 집합에 포함시켰습니다.

`get_active_pair`(진행 중 중복 방지)는 원래 종결 상태를 제외하고 있어 수정 불필요였습니다.
`GET /api/link-jobs/{id}`는 status를 그대로 통과시키므로 외부 오케스트레이터에는 이제
`failed` 대신 `declined`가 보입니다.

## 5. `language` / `engine_variant` 분리 — 백필까지 했습니다

`sync_results`에 `engine_variant VARCHAR(16)`를 추가하고, `language`에는 순수 언어만
저장합니다. 엔진 내부 캐시 키(`ctc_engine.py`의 `{lang}_mms`)는 그대로 두고 **DB로 흘러가는
값만** 갈랐습니다.

소급 백필은 컬럼이 처음 생기는 시점에 1회 실행됩니다(멱등):

```sql
UPDATE sync_results
   SET language = SUBSTR(language, 1, LENGTH(language) - 4), engine_variant = 'mms'
 WHERE language IS NOT NULL AND SUBSTR(language, -4) = '_mms';
```

`LIKE '%_mms'`를 안 쓴 이유: SQLite `LIKE`에서 `_`는 **단일 문자 와일드카드**라 `jamms` 같은
값도 걸립니다. 실제로 그런 값은 없지만 백필은 되돌릴 수 없어 정확 비교로 갔습니다.

읽기 지점도 전수 정리했고(`_mms` 리터럴 비교는 `ctc_engine.py` 외에 없음을 확인),
`SyncLookupResponse`에 `engine_variant`를 **additive로** 추가했습니다(기존 필드 무변경 —
구버전 확장은 모르는 필드를 무시합니다).

**교차 영상 캐시 복사 경로**(`_complete_from_cache_db`)가 누락 지점으로 나왔습니다. 새 정렬이
아니라 기존 행 복사라, 기본값에 맡기면 원본의 변형 정보가 사라집니다 — 원본 값을 그대로
옮기게 했습니다.

`models.py` 컬럼과 `config/settings.py` 양쪽에 남겼습니다: **정렬된 줄들의 평균 CTC 자기

## 7. 고아 잡 리퍼 — 넣었습니다

기존 리스 스위퍼(`_sweep_expired_leases`)가 **인메모리 `_LEASES`를 쥔 잡만** 커버한다는 것이
사각지대였습니다. 인프로세스 워커와 "번역 대기" 구간은 리스 없이 정상적으로 `processing`이라
그 스위퍼에 안 잡힙니다 — 보고해 주신 사고(stage="번역 대기", 6.3시간)가 정확히 이 구멍입니다.

- 기준 컬럼은 `created_at`이 아니라 **`Job.updated_at`**입니다. 진행 중인 잡은 2~4초 간격
  하트비트로 이 값이 계속 갱신되므로, "오래 걸리는 정상 잡"과 "하트비트가 끊긴 고아 잡"이 갈립니다.
- TTL 기본 50분, 5분 주기 스윕, `EVERYRIC_SERVER_ORPHAN_JOB_TTL_MIN`으로 조정(0이면 비활성).
- 회수는 `update_status_if(expected=("processing",))` 조건부라 경합해도 정상 완료를 덮지 않습니다.
- 회수 시 사용자에게는 "서버가 정체된 작업을 회수했어요 — 다시 시도해 주세요"가 보이고,
  로그에 잡 id·정체 시간·stage·progress를 남깁니다.

지적하신 폴링 폭주(48시간 10,779회)는 잡이 종결되면 클라이언트가 폴링을 멈추므로 함께
해소될 것으로 봅니다.

## 8. `:8300` 바인딩 — 좁혀도 무해합니다 (실측)

**결론: 좁혀도 되는 것이 맞고, 저희 쪽에서 끊길 사용처는 없습니다.**

각 클라이언트의 실제 접속 경로를 확인했습니다.

| 구성요소 | 접속 경로 | 좁혔을 때 |
|---|---|---|
| GPU 워커 | `EVERYRIC_WORKER_SERVER_URL=http://127.0.0.1:8300` (동거) | 영향 없음 |
| 크롬 확장 | `https://everyric.moref.co` → 터널 → 게이트웨이 | 영향 없음 |
| AE 패널 | 동일(기본값 같음) | 영향 없음 |
| 운영 스크립트(`bulk_ingest`·`verify_regen`) | `127.0.0.1:8300` | 영향 없음 |

원인도 확인했습니다 — **systemd 유닛은 이미 `EVERYRIC_HOST=127.0.0.1`로 설정돼 있는데
`.env`가 `0.0.0.0`으로 덮고 있습니다.** 코드 수정 사안이 아니라 배포 시 `.env` 한 줄입니다.
게이트웨이(`127.0.0.1:8310`)는 이미 루프백 전용으로 정상입니다.

테일넷에서 8300 직결이 필요한 저희 용도는 없습니다(ssh + localhost로 대체 가능). 적용
시점은 그쪽 판단에 맡깁니다.

## 9. `translate` 총예산 — 넣었습니다

진단하신 그대로였습니다. 저희가 테스트로 정량 재현했습니다: 8줄이 매번 전원 미스매치되는
응답을 받으면 예산 없이 **15회** 왕복까지 갑니다(depth0:1 + depth1:2 + depth2:4 + depth3:8).

- `TranslationBudget` — 요청 1회당 **누적 왕복 횟수**(기본 8)와 **누적 소요시간**(기본 90초,
  확장 타임아웃 120초보다 낮게)을 추적하는 공용 게이트.
- 재귀 트리 전체(`_translate_lines → _run_batches → _translate_batch → _retry_low_quality
  → _request_completion`)에 같은 인스턴스를 전달.
- 소진 시 **예외 없이** 그 시점까지의 최선 결과로 정상 반환합니다 — 부분 번역이 무번역보다
  낫다는 판단입니다. 경고 로그 1회.
- 기존 개별 재시도(미스매치 복구·저품질 재요청·429 백오프)는 **로직 변경 없이** 그대로 두고
  그 위에 예산만 얹었습니다. 각각은 정당하다는 지적에 동의합니다.

#7과 같은 뿌리인지는 저희도 확정하지 못했습니다. 다만 리퍼가 들어갔으므로 같은 뿌리였다면
증상은 더 이상 6시간 정체로 남지 않습니다.

## 감사 범위 밖에서 함께 들어간 것

모델 스택 교체 작업이 진행 중이라, 같은 마이그레이션에 두 가지를 얹었습니다. 그쪽 원장·대시보드에
영향이 있을 수 있어 알려 드립니다.

- **`sync_results.engine_version`** — 새로 만드는 싱크에 스택 식별자를 새깁니다(현재
  `"mms-htdemucs-1"`). 기존 행은 NULL(=구세대)로 두고 소급 백필하지 않습니다. 스택 교체 후
  "이 싱크가 어느 스택 산출물인가"를 시각 추산이 아니라 값으로 판정하기 위한 것입니다.
- **`sync_result_versions` 테이블** — 재처리로 교체된 **직전 1세대**만 보관하고
  `GET /api/sync/{video_id}/previous`로 조회합니다. 새 스택 배포 후 품질 A/B 비교와 롤백
  판단에 쓸 예정입니다. video_id를 PK로 둬 "영상당 1건" 불변식을 DB 레벨에서 강제합니다.
  초기화(`DELETE /api/sync/{video_id}`) 시 같은 트랜잭션에서 함께 삭제됩니다.

2. `.env`의 `EVERYRIC_HOST`(#8) — 적용하실 거면 이때가 적기입니다.

한 가지 관측 사실을 정보로만 남깁니다(조치는 그쪽 판단): 서버 저장소의 `master`에

pull하실 때 머지가 생길 텐데, 그 과정에서 강제 리셋이 들어가면 그 커밋은 어디에도 사본이
